## 1. What We Are Building (Plain English)

A customer on a product page clicks **✦ Virtual Try Room**. Three things happen:

1. **The product is silently added to their cart** and the **cart drawer slides in** — a gentle "it's in your bag" nudge (conversion psychology).
2. **The try-on modal opens.** If they are **not signed in**, they see **"Sign in with Google to try on"**.
3. After Google login, they upload a photo and see themselves wearing the outfit — generated by fashn.ai.

**Limits (cost safety):**
- Each Google account: **3 free try-ons per 24 hours** (rolling window, auto-resets).
- The whole website: **20 try-ons per calendar day** total (hard cost cap).
- When limits are hit, a friendly screen appears (no payment — just "come back tomorrow" / WhatsApp us).

**No charging. No payment gateway. No credits.** Those come in a later phase once the bank/payment gateway is ready.

## 4. Database Design (Supabase)

### New table: `try_on_usage`

One row per **successful** try-on. Counting rows answers both limit questions — **no reset job / cron needed** (we just count recent rows).

| Column | Type | Purpose |
|--------|------|---------|
| `id` | uuid (PK, default gen_random_uuid) | Row id |
| `user_id` | uuid → `auth.users.id` | Which Google account |
| `user_email` | text | Saved for your records / analytics |
| `product_slug` | text | Which product was tried (analytics) |
| `category` | text | ladies-suits / kids-formal (analytics) |
| `created_at` | timestamptz (default now()) | Used for the 24h / daily windows |

**How limits are computed (no stored counters, just queries):**
- **Per-user (rolling 24h):** `count(*) where user_id = ? and created_at > now() - interval '24 hours'` → must be `< 3`
- **Global (calendar day):** `count(*) where created_at >= date_trunc('day', now())` → must be `< 20`

**Security:** The API route uses the **service-role** Supabase client (server-only) to read counts and insert rows. Row Level Security stays ON; the table is never touched from the browser.

**Tunable constants** (easy to change later, will live in the API route):
```
PER_USER_DAILY_LIMIT = 3
GLOBAL_DAILY_LIMIT    = 20
PER_USER_WINDOW       = 24 hours (rolling)
```

## 5. Google Login (Supabase OAuth — Free, No Billing)

**Important:** This is **Google OAuth** (using Gmail as a login). It is **100% free** and has **nothing to do with Google Cloud billing or Vertex AI**. Creating OAuth credentials does not require a payment card.

### One-time setup (you do this in dashboards, no code)
1. **Google Cloud Console** → APIs & Services → Credentials → Create **OAuth Client ID** (Web application). This is free. Copy the **Client ID** and **Client Secret**.
2. Add the Supabase callback URL to the "Authorized redirect URIs" (Supabase shows you the exact URL).
3. **Supabase Dashboard** → Authentication → Providers → **Google** → paste Client ID + Secret → Enable.

That's it — the credentials live in Supabase, not in your code or `.env.local`.

### Code side (built during implementation)
- `supabase.auth.signInWithOAuth({ provider: "google" })` triggers the login.
- A new route `app/auth/callback/route.ts` handles the return from Google (standard Supabase SSR pattern).
- Because login is required **before** uploading, the full-page redirect during OAuth does not lose any uploaded photo (nothing is uploaded yet at that point).

## 6. Cart Integration (The "Slide-In Bag" Feature)

Your cart already supports this with zero new infrastructure:
- `cart-store.ts` → `addItem()` and `openDrawer()` already exist.
- `add-to-cart-section.tsx` already imports both.

**CONFIRMED behavior (owner decision, 11 Jun 2026):** When "✦ Virtual Try Room" is clicked, ALL of this happens together:
1. `addItem(product)` — product enters the bag (badge updates).
2. `openDrawer()` — the **cart drawer slides in from the right** (the same drawer the navbar bag icon opens).
3. The **try-on modal opens ON TOP** of the drawer (foreground).

The cart drawer sitting **behind** the modal is intentional and fine — it does not need to be fully visible while the modal is open.

**The key moment:** when the customer **closes the try-on modal**, the cart drawer is **still open on the right**, showing the product is already in their bag. This is the conversion nudge the owner wants.

**Every click adds the product** — yes, intentional. Each Try On click re-adds + re-opens the drawer. (Cart items are normal/removable, so duplicates are not a concern.)

**Technical note (already verified):** z-index supports this with no conflict — try-on modal is `z-[100]`, cart drawer is `z-[48]/[49]`. Modal naturally sits above. No new infrastructure: `cart-store.ts` already exposes `addItem` + `openDrawer`, both already imported in `add-to-cart-section.tsx`.

## 7. Modal States (UI)

The modal state machine grows to handle auth + limits:

| State | When | What the user sees |
|-------|------|--------------------|
| `needsLogin` | Not signed in | "Sign in with Google to try on" + Google button |
| `upload` | Signed in, ready | Upload photo + "2 of 3 free tries left today" counter |
| `loading` | Generating | Spinner + rotating messages (fashn.ai ~5–17s) |
| `result` | Success | Side-by-side: your photo · you in the outfit |
| `limitReached` | Used 3/3 today | "You've used today's 3 free try-ons. Come back tomorrow, or WhatsApp us." |
| `globalBusy` | Site hit 20/day | "Our virtual fitting room is very busy today — please try again tomorrow." |
| `error` | Failure | Friendly error + Try Again |
